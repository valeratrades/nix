# Kernel 6.12 → 7.0: an independent fan lever for `longevity`

Status: **done and live as of 2026-09-01.** Gates 1 and 2 passed; Gate 3 produced a
negative result that changed the conclusion but not the design. `longevity` is now
boost-off + `balanced`, and fans are driven reactively by `thermal-guard` rather than
pinned — see §6, which is a deliberate departure from the original plan.

## The problem this exists to fix

`optimize_for longevity` means "no boost, max airflow". It delivers only the second
half, and pays for it. `thermal.nix` sets `platform_profile=performance` purely for the
fan curve, and that same knob is the power-limit knob.

| `platform_profile` | avg core clock | package power |
|---|---|---|
| `quiet` | 527 / 701 MHz | 33 W |
| `performance` | 1955 / 1956 MHz | 40–41 W |

*(boost=0, `scaling_max_freq=2501000`, 24 spinner threads. Measured 2026-09-01.)*

So the mode named for component lifespan licenses +8 W and a 3× clock ceiling.

## 1. `legion_laptop` was loading against the wrong EC register map

This is a Legion R9000P ADR10 (`83LV`, BIOS `RLCN29WW`). `legion_laptop` has no entry
for it. `thermal.nix` force-loaded it anyway:

```
legion PNP0C09:00: legion_laptop is forced to load and would otherwise not be loaded
legion PNP0C09:00: Using configuration for system: GKCN     <- a 2021-era Legion's EC map
legion PNP0C09:00: Skipped checking embedded controller id
```

Every EC-mediated knob was consequently inert, and silently so:

- `fan1_input` latched at 23135 against its own `fan1_max` of 10000
- non-monotonic fan curve readings
- `fan_fullspeed` writes accepted and discarded
- `legion_cli maximumfanspeed` enable reads back `False`

**Fan RPM was unobservable and uncontrollable.** `platform_profile` worked only
because it is ACPI, not EC.

## 2. `lenovo-wmi-other` provides the lever — and it is profile-independent

Verified by reading `drivers/platform/x86/lenovo/wmi-other.c` out of the 7.0.3 source
tarball, not by assumption:

- `LWMI_OM_HWMON_NAME "lenovo_wmi_other"`, registered via
  `hwmon_device_register_with_info`, exposing `fanN_input` / `fanN_target` (RW,
  `0` = firmware auto) / `fanN_min` / `fanN_max` / `fanN_div`.
- `CONFIG_LENOVO_WMI_TUNING` is a tristate whose deps (`ACPI_WMI`, `HWMON`,
  `FW_ATTR_CLASS`, `LENOVO_WMI_CAPDATA`, `LENOVO_WMI_EVENTS`, `LENOVO_WMI_HELPERS`)
  are all satisfiable; nixpkgs' `autoModules` answers `m`.
- **The decoupling:** `LWMI_ATTR_ID_FAN_RPM(x)` is composed of `DEV_ID | FEAT_ID |
  TYPE_ID` only. It never `FIELD_PREP`s `LWMI_ATTR_MODE_ID_MASK`, i.e. it is issued
  with thermal mode `0` / `NONE`. The PPT attributes at `wmi-other.c:722,793,852` *do*
  carry the live thermal mode. Fan control is therefore not scoped to a profile.

We use the **fan** path only, never PPT: per `lenovo-wmi-gamezone.rst`, PPT attributes
take effect only under the `custom` profile — "if another profile is set, the BIOS will
override any user PPT settings".

`wmi-gamezone.c:339-346` sets the choice bits: `low-power`, `balanced`, `performance`,
`custom`, plus `max-power` behind a BIOS quirk table. **Never write `max-power`** —
upstream ships that table because "setting it will cause undefined behavior".

## 3. The plan said 7.1.5; nixpkgs has 7.0.3

`linuxPackages_7_1` does not exist in the pinned nixpkgs — the ceiling is
`linuxPackages_7_0` = 7.0.3 (6.17 and 6.16 are removed as EOL; 6.18 is present).
Every capability above was then re-verified against the 7.0.3 tree specifically, and
all of it is there. The version number was wrong; the premise was not.

## Not the cause (retracted)

Both from `2026-07-26_cpu-thermals.md` §4, retracted for the second time:

- **"the PPT increase is the unavoidable price of airflow"** — it rested on a single
  test, `legion_cli maximumfanspeed`, and that test was invalid. It wrote a GKCN offset
  to an RLCN EC. A negative result from an instrument pointed at the wrong address is
  not a negative result.
- **"moving to a newer kernel is not known to deliver the drivers"** — answered. The
  driver is in-tree and `=m`.

## Changes applied — step 1 (kernel + removals, policy untouched)

Staged separately from the policy flip so that a 7.0 boot failure could be judged on its
own. `lenovo-legion-module` could not be deferred:
`lenovo-wmi-gamezone` binds the same GUID (`887B54E3-…`) and registers the same
`platform_profile` handler, so the two cannot coexist.

- `configuration.nix` — `linuxPackages_6_12` → `linuxPackages_7_0`.
- `configuration.nix` — dropped `extraEntries."gen34-safe.conf"`. Its target store path
  no longer exists, and systemd-boot resolves `linux /nix/store/…` relative to the ESP,
  which has no `nix/store` — it could never have booted.
- `thermal.nix`, `hardware-configuration.nix` — dropped **both** `extraModulePackages`
  sites and the `options legion_laptop force=1` block. Two sites, same trap as
  `power-profiles-daemon` in `2026-07-26`.
- `thermal.nix` — dropped both udev rules. `optimize_for` runs under `sudo -E`, so the
  wheel grant was unused, and `SUBSYSTEM=="acpi"` is not known to still match.
- `thermal.nix` — `legion-battery-conservation` no longer shells out to `legion_cli`.
  `conservation_mode` is owned by `ideapad_acpi` (`/sys/bus/platform/devices/VPC2004:00/
  driver → ideapad_acpi`), untouched by the removal, so the unit writes it directly.
- `thermal.nix`, `home.nix` — dropped `pkgs.lenovo-legion`.
- `other.fish` — dropped `disable_fan` / `enable_fan`. Already dead: `legion_hwmon`
  exposes `pwm1_mode`, never `pwm1`.
- `optimize_for.rs` — `Mode::Quiet` `"quiet"` → `"low-power"`; `expect` strings that
  named `legion_laptop force=1` now name the driver that actually backs the file.

Then, after Gate 2 — step 3:

- `thermal.nix` — `legion-longevity` sets `balanced`, and touches no fans.
- `thermal.nix` — `thermal-guard` gains `set_fans`, `FAN_HIGH`/`FAN_LOW`, and the
  startup state reset. Its `description` and the two stale throttle log lines (which
  said 90C/80C against 85/75 thresholds) were corrected at the same time.
- `thermal.nix` — `sensor-sampler` gains `wmi=` and the `fan=` field.
- `optimize_for.rs` — `Longevity` → `balanced`; `set_profile` asserts against
  `platform_profile_choices`; "fans" relabelled "profile" in output, since a mode no
  longer says anything about airflow.

Rollback pins, against `nh.clean`'s weekly `--keep-since 7d`:

```
/nix/var/nix/gcroots/pin-gen572-booted-6.12   -> …ahrly42g…  (was /run/booted-system)
/nix/var/nix/gcroots/pin-gen573-last-6.12     -> …ibaznj0r…  (was /run/current-system)
```

572 is pinned *because* it is the booted one — the plan reached the same guarantee via
a reboot-and-verify before pinning 573; pinning the already-booted generation gets it
without the reboot. Recovery:

```fish
sudo /nix/var/nix/gcroots/pin-gen572-booted-6.12/bin/switch-to-configuration boot
```

## 4. Gate 1 — 7.0 boots clean

`uname -r` 7.0.3. `legion_laptop` absent; `lenovo_wmi_gamezone`, `lenovo_wmi_other`,
`lenovo_wmi_capdata`, `lenovo_wmi_events`, `lenovo_wmi_helpers` and `ideapad_laptop` all
loaded. `conservation_mode` reads 1 off the raw `VPC2004:00` write. All four units
active. nvidia intact.

Two things that look alarming and are not:

- **DMCUB errors are not a regression.** `amdgpu … DMCUB error - collecting diagnostic
  data` appears 5× this boot against **15×** on the last 6.12 boot. It is why 6.12 was
  pinned in the first place, and 7.0 is strictly better on it, not worse.
- **nvidia did not move.** Still 595.71.05, not 595.84 — `hardware.nvidia.package`
  resolved to the same driver across the bump. That shrinks watch-list item 1: the
  driver is a constant, so any display regression points at the kernel alone.

## 5. Gate 2 — the lever is real, all three conditions

The hwmon registers as `lenovo_wmi_other` with three channels (fan3 is not exposed),
and unlike `legion_hwmon` the numbers are immediately sane — monotonic, inside their
own advertised bounds:

| | `fan1` | `fan2` | `fan4` |
|---|---|---|---|
| `_min` | 1600 | 1600 | 1600 |
| `_max` | 5100 | 5100 | 6500 |
| `_div` | 100 | 100 | 100 |

**A — `fanN_input` is live.** Idle → 45 s of 24-thread load → +30 s:
`fan1` 2200 → 3100 → 3400, `fan4` 2500 → 4400 → 5000. Tracks load, never exceeds `_max`.
Compare 6.12: latched at 23135 against a `fan1_max` of 10000.

**B — `fanN_target` is honoured.** Writing `fanN_max` on an *idle* machine:

```
targets read back: 5100/5100/6500
 +5s: fan1=3700 fan2=3600 fan4=4600
+10s: fan1=4800 fan2=4700 fan4=6100
+20s: fan1=5100 fan2=5100 fan4=6500   <- exactly _max, from idle, audibly
```

Not accepted-and-discarded. This is the thing `fan_fullspeed` and `maximumfanspeed`
could never do.

**C — independent of `platform_profile`.** With the targets pinned, walking the profile
down:

```
performance: fan1=5100 fan4=6500   targets=5100/6500
balanced:    fan1=5100 fan4=6500   targets=5100/6500
low-power:   fan1=5100 fan4=6500   targets=5100/6500
then target=0 -> fan1=3600 fan4=4700 (firmware curve resumes)
```

The premise holds outright. It also answers an open question: **a profile write does not
reset `fanN_target`.**

`platform_profile_choices` is `low-power balanced performance max-power custom` — note
`max-power` *is* offered on this BIOS. Still never write it.

### The retraction Gate 2 forced: `performance` never gave max fans either

At idle in `performance`, `fan1_input` read 2200 of a possible 5100 — **43%**. Under
load it reached 3400. The profile that `longevity` was paying +8 W to select was not
delivering max airflow at any point. The old config's stated goal ("fans max") was never
actually achieved on 6.12; it was unobservable, so nobody could tell.

## 6. Gate 3 — the power saving did not materialise, and the design changed anyway

Interleaved, boost off, 24 threads, 100 s per run:

| profile | avg core clock | package power |
|---|---|---|
| `balanced` | 2258 MHz | 34 W |
| `performance` | 2287 MHz | 35 W |
| `balanced` | 2320 MHz | 44 W |
| `performance` | 2280 MHz | 44 W |

**`balanced` and `performance` are indistinguishable on 7.0 at boost=0.** The 33 W /
41 W split measured on 6.12 does not reproduce under `lenovo_wmi_gamezone`; the drift
between the two pairs (34→44 W) is thermal soak, and it is larger than the difference
between the profiles. So the headline "+8 W for airflow" charge, which motivated this
whole change, **is not a cost on 7.0**. `balanced` is kept regardless: it is the honest
name for a longevity envelope and it is never *worse* than `performance`.

What the change did buy is the thing that survives: fans answer to temperature instead
of to a power profile.

### Fans are reactive and interpolated, not pinned

The plan's end state pinned `fanN_target = fanN_max` for `longevity`. Rejected on the
owner's instruction, and correctly: noise is not a constraint here, but idle fan power
and the fans' own waste heat are, so running at 5100 RPM while browsing buys nothing.

`thermal-guard` is now their sole owner, driving them off the same `k10temp` read and in
the same loop it already used for frequency. No new unit.

```
        58-59C      60C    65C                          78C            85C
   idle floor ────── RELEASE ─ ENGAGE ═══════ ramp ═════ TOP ────────── TEMP_HIGH
   └─ firmware's own curve ──┘   └─ interpolated, per channel, ~125 RPM/°C ─┘
                                                    fanN_max ┘       freq to 60% ┘
```

`fanN_target` accepts any RPM in `[fanN_min, fanN_max]` quantised to `fanN_div`, not just
the extremes — so the honest lever is a ramp, and the earlier binary version was leaving
most of it unused.

**Four calibrations, three of them wrong.** All rejected on measurement, not taste:

| band | outcome |
|---|---|
| 65/58 switch | release sat on the 58-59C idle floor; fans pinned permanently |
| 72/65 switch | band inside the working range; flapped max↔auto 6× in 20 min |
| 78/68 switch | still inside it; flapped 4× in 11 min |
| 78/62 switch | one spin-up per session — but max-or-nothing, and 62 is nearly idle |
| **65→78 ramp** | **one engage, no flapping, and it never reaches max** |

Under a real session the CPU sweeps 67-80C continuously, so *any* narrow band placed in
that range cycles and a wide one degenerates to max-or-nothing. Interpolating deletes the
boundary that was doing the flapping: a 1 °C drift now moves the fans ~125 RPM instead of
2900.

**`RAMP_BASE` (50 °C) is below `FAN_ENGAGE` (65 °C) on purpose.** It is the notional
temperature at which the ramp would sit at `fanN_min`; placing it below the engage point
means the *first* interpolated value already exceeds what the firmware curve was
delivering there, so taking over can never drop RPM. Setting `RAMP_BASE = FAN_ENGAGE`
would drop fan1 from ~2500 to 1600 exactly as the machine got hotter.

Handing back below `FAN_RELEASE` is not laziness — the firmware curve is fine at the
quiet end, and it is already proportional, so there is nothing to reimplement down there.
It is only *above* ~65 °C that it is too slack.

**Measured, live, `balanced`, boost off** — `fan1_input` tracked `fan1_target` exactly at
every step:

| cpu | firmware curve gave | ramp gives (fan1 / fan4) | fan1 as % of max |
|---|---|---|---|
| 58-60C | 2100-2400 | (firmware, released) | 45% |
| 67C | 2700-2900 | 3700 / 4500 | 73% |
| 68C | — | 3800 / 4700 | 75% |
| 69C | ~2900 | 3900 / 4900 | 76% |
| 70C | — | 4100 / 5100 | 80% |
| 72C | 3100 | 4300 / 5400 | 84% |
| 77C | 3100-3700 | — | — |
| 78C | 3700 | 5100 / 6500 | 100% |

The consequence is the point: with the firmware curve the CPU drifted 67 → 77 °C over
eight minutes at load ~3. With the ramp it sits at **67-72 °C**, and a load spike to
**13.1** peaked at 72 °C — i.e. it never needed `fanN_max` at all, and never came near
the 85 °C throttle.

Writes are issued only on a whole-degree change. At ~125 RPM/°C the sub-degree difference
is below `fanN_div`, so re-issuing three WMI calls every 2 s would be pure overhead.

### A restart used to strand the hardware

`throttled=0` / `fans_engaged=0` describe the hardware, but the hardware outlives the
process — fan targets and `scaling_max_freq` both survive a restart. A crash mid-excursion
would leave fans pinned (or the CPU throttled) while a fresh loop believed it was neither,
and *neither release branch would ever fire again*. Observed live: after a rebuild the
fans sat at 5100 RPM at 58 °C with no event logged.

Fixed by driving the hardware to match the assumption at loop start rather than assuming
it: `set_fans auto` + `set_freq $(base)` before the `while`. Verified — targets read
`0/0` and fans dropped to 2100 RPM within seconds of the next restart.

## End state (live)

| mode | boost | profile | fans |
|---|---|---|---|
| `Quiet` | off | `low-power` | thermal-guard |
| `Longevity` (boot default) | off | `balanced` | thermal-guard |
| `Performance` | on | `performance` | thermal-guard |

Fans are not a per-mode setting. `thermal-guard` owns them in every mode, on measured
temperature — including `Quiet`, which is safe because `low-power` caps the machine far
below the 65 °C engage point, so silence is never actually broken.

`optimize_for` therefore *lost* a dimension instead of gaining one: modes stay
`(boost, profile)`, `Restore` needs no `fan_targets`, and there is no `set_fans` in the
Rust at all. `set_profile` did gain the assert against `platform_profile_choices` — it is
the single point every write including `Drop` routes through, so a driver-side rename
becomes a panic instead of a silent no-op.

## Measurements

| kernel | profile | boost | avg core clock | package power | `fan1_input` |
|---|---|---|---|---|---|
| 6.12 | `quiet` | off | 527 / 701 MHz | 33 W | unreadable (latched 23135) |
| 6.12 | `performance` | off | 1955 / 1956 MHz | 40–41 W | unreadable (latched 23135) |
| 7.0 | `balanced` | off | 2258 / 2320 MHz | 34 / 44 W | 5100 = `fan1_max` |
| 7.0 | `performance` | off | 2287 / 2280 MHz | 35 / 44 W | 5100 = `fan1_max` |

Idle reference, 7.0, `balanced`, load ~4: cpu 58–60 °C, 26–31 W, fans 2100–2300 RPM on
the firmware curve.

Two things to read off this table. 7.0 `balanced` runs the machine ~300 MHz *faster*
than 6.12 `performance` did at the same boost setting, so the profiles are not
comparable across the driver change. And the 6.12 fan column was never a measurement at
all — it was a latched register.

## Watch list

1. **Fan control efficacy after suspend/resume.** The load-bearing risk. If `fanN_target`
   stops being honoured, `longevity` silently becomes balanced-with-idle-fans, worse than
   6.12. `sensor-sampler`'s `fan=` field is the standing check:
   `journalctl -u sensor-sampler | tail` — `fan=` should track the ramp table above, not
   the firmware column. Note the re-assert is now only on a whole-degree change, so a lost
   write persists until the temperature moves 1 °C rather than for 2 s.
2. **Threshold calibration.** 72/65 is tuned to a 58–59 °C idle floor under today's
   background load. If that floor moves (Discord alone is 67% of a core — see
   `2026-07-26` §Discord), the fans either pin permanently or stop helping. Re-measure,
   do not re-guess.
3. **`legion_laptop` removal** lost `gsync`, `overdrive`, `cpu_oc`, `*_powerlimit`,
   `legion_hwmon`. Nothing referenced them; the loss is silent.
4. **`max-power` is offered** on this BIOS, unlike the upstream default. Never write it —
   upstream ships the quirk table because "setting it will cause undefined behavior". The
   `set_profile` assert does not protect against this; it only checks membership.
5. **Battery conservation** moved off `legion_cli` to a raw `conservation_mode` write.
   Reads 1. BAT0 should plateau near 80%. The `rapidcharge` mutual exclusion is gone.
6. **nvidia** stayed at 595.71.05 across the bump, so it is *not* a confound. The 6.18
   breakage recorded in `configuration.nix` was never diagnosed and 7.0 does not appear to
   share it.
7. **Panel backlight** came up at 1% (`amdgpu_bl2` = 655/65535). See below — open.
8. **`pcie_aspm.policy=performance`** — 7.0 is far past the mt7925 fix that
   `2026-06-05_slow-shutdown.md` was waiting on. Retest separately.
9. Inherited from `2026-07-26`: `processor.max_cstate=1` removal, `amd_pstate=active`,
   two unlogged hard resets (08-03, 08-22) still unexplained.

## The panel came up at 1% brightness — a mask that never masked

Not caused by the kernel bump, but exposed by it.

`/sys/class/backlight/amdgpu_bl2` read **655 of 65535** — 1.0%. It is the real panel
(`card2-eDP-1`, the connected eDP on the amdgpu iGPU); `nvidia_0` (5/100) is a second,
irrelevant device on the dGPU that only exists because `nvidia_wmi_ec_backlight` is newly
loaded on 7.0.

The cause is not the kernel. `configuration.nix` carried

```nix
"systemd-backlight@.service" = { enable = false; unitConfig.Mask = true; };
```

and **it never masked anything.** `unitConfig.Mask` is not a unit directive — the
generated drop-in contains only NixOS's standard `Environment=` lines and
`X-RestartIfChanged=false`. Verified live:
`systemctl is-active systemd-backlight@backlight:amdgpu_bl2.service` → `active`, and the
instances ran on this boot. Masking a *static template* unit needs
`systemd.services."systemd-backlight@".enable` to actually produce a mask symlink, which
`enable = false` on an instantiated template does not.

So systemd-backlight has been saving and restoring brightness the whole time, and what
it restored was stale:

```
/var/lib/systemd/backlight/pci-0000:06:00.0:backlight:amdgpu_bl1 = 255   (Apr 30)
/var/lib/systemd/backlight/pci-0000:06:00.0:backlight:amdgpu_bl2 = 100   (Sep 1)
```

against a `max_brightness` that is now **65535**. The device also renumbered
`amdgpu_bl1` → `amdgpu_bl2` when `legion_laptop` stopped registering its own LED, so the
new instance started from no useful history at all.

ABM is ruled out: `card2-eDP-1/amdgpu/panel_power_savings` reads 0, and
`amdgpu.abmlevel=0` remains commented out in `configuration.nix` ("breaks brightness
control").

**Fix: the dead block was deleted.** Removing a proven no-op cannot change behaviour —
systemd-backlight was already running and will now persist a sane value across boots,
which is precisely its job. Brightness was set to 39321/65535 (60%) so it has something
correct to save.

If it turns out the original intent really was to keep systemd-backlight out of the way,
that has to be done properly and for a recorded reason; both commits that touched the
block have the message `_`, so no reason survives.
