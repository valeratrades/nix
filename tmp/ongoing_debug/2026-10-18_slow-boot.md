# Boot: power button → Chrome's restored tab loaded, ~59s (2026-10-18)

## INCIDENT 2026-10-19: generations 629-632 booted to a dead `v-laptop login:` prompt
What I did: to drop getty's `Type=idle` 5s wait, I set `systemd.services."getty@tty1".serviceConfig.Type`.
NixOS's autologin lives in `getty@.service.d/overrides.conf`; my override became `getty@tty1.service.d/overrides.conf`.
Same file name → systemd uses the instance drop-in *instead of* the template's, not alongside it.
tty1 fell back to stock `ExecStart=/usr/bin/agetty` → `agetty: can't exec /bin/login` → no autologin and no way to log in on tty1.
(tty2 was unaffected: Ctrl+Alt+F2 gave an autologin shell.)

Why my checks missed it: `systemd-analyze verify` only checks syntax, and I read the drop-in file instead of the merged unit.

Never again:
- Never override an instance (`foo@bar`) of a template NixOS already customizes; set it on the template (`getty@`).
  The eval-time assertion in os/nixos/configuration.nix rejects any such pair.
- `system.preSwitchChecks.gettyAutologin` (os/nixos/shared-services.nix) refuses `nixos-rebuild boot/switch` unless
  tty1's merged unit, as systemd itself loads it (`systemd --test`), execs NixOS's `--autologin` getty. Confirmed:
  rejects 632, passes 628 and the fix.
- Boot-path changes get verified on the merged unit, not on the file I wrote.
- If stuck at `login:` again: Ctrl+Alt+F2, or pick an older generation in systemd-boot (spam Space at power-on).

Measure: `journalctl --user -t boot-timeline` (one line per boot, home/scripts/boot_timeline.mjs).
Seconds since kernel start; firmware+loader come before the kernel.

## Sway (start → sway-session.target)
Boot 2026-10-20 02:13 sway log (`-d`), seconds since sway start:
```
0.026 ─ Creating multi-GPU renderer (card1 nvidia)
      ├ 0.53 glvnd loads every EGL vendor's libs cold (mesa + nvidia)  ← paid by whichever GPU inits first
      ├ 0.15 nvidia EGL display + GBM                                   ✂ deferred
0.700 ├ 0.14 AMD EGL/GLES2 (primary renderer)
0.898 ─ `font pango:Sans 6` ── 0.55 (1.4 on the earlier boot) fontconfig cold load  ✂ prewarmed
1.497 ─ backend start, libinput, connector scan (card1 0.18)
2.026 ─ one atomic commit for eDP-1 + HDMI-A-1 ── 1.22  (split per GPU unknown; HDMI part ✂ deferred)
3.317 ─ outputs committed
```
**font**: not a stale cache. NixOS ships a pre-built system cache; the cost is fontconfig touching ~580 font dirs
(google-fonts alone is a 17.7MB cache file of the 22MB) + ~2600 cache/.uuid opens, all cold at boot.
pango `get_metrics("Sans 6")` (what sway's `font` does), libs already resident:
cold 0.29-0.53s, warm 0.07s; without google-fonts cold 0.30, warm 0.03 (so it's the cold dirs, not the font count).
~/.cache/fontconfig held 89MB of stale caches (7 fontconfig versions, all written 2026-10-16 06:xx by some
one-off `fc-cache`): +0.15s cold, deleted. Cause of that `fc-cache` run unknown.
Fix: `sway-prewarm.service` (os/nixos/desktop/programs/sway.nix) runs `fc-match -s Sans` as the user at
multi-user, ~10s before sway. After `drop_caches` + prewarm: 0.07s (= warm).
Same unit runs `eglinfo -B -p surfaceless`: full `eglinfo` cold 0.58-0.90s → 0.41s after it (warm 0.35).

**NVIDIA**: wlroots 0.19 can add a GPU after start: with `WLR_DRM_DEVICES` *unset* it installs a DRM
monitor (backend/drm/monitor.c) that creates a secondary DRM backend + multi-GPU renderer on a udev `add`
of a new card (duplicate adds of already-open cards are skipped). With `WLR_DRM_DEVICES` set there's no
monitor, so pinning AMD would lose HDMI for the session. Card enumeration happens once, in
`wlr_backend_autocreate`, before sway binds its socket.
So nvidia_drm is blacklisted against udev's PCI-alias autoload and `nvidia-drm-late.path` modprobes it
once `/run/user/*/wayland-*` exists. sway starts on AMD alone; card1 registers ~1-3s later (nvidia_drm's
own init took 2.8s at boot: 5.94→8.73) and HDMI comes up through the hotplug path, plugged or not
(unplugged = normal connector hotplug on the added card). If nvidia_drm wins the race anyway, sway just
enumerates it as before.
Side effects: amdgpu now probes first (card numbering changes, and the eDP-1/eDP-2 race from
home/config/sway/README.md should settle on amdgpu = eDP-1); ws 1/2/3/6/7/0 start on eDP and sway moves
them to HDMI when it appears; adding card1 blocks sway's loop for its EGL init (~0.15s warm) after startup.
Not verified on a real boot yet: check `~/.sway.log` (needs `vars.debug`) for
`Creating DRM backend for /dev/dri/card* after hotplug`, and `swaymsg -t get_outputs` for HDMI-A-1.
Not deferrable: the 0.53 glvnd vendor load (sway's AMD renderer pays it too), and eDP's own modeset.

`-d` now comes from `vars.debug` via `programs.sway.extraOptions`; stderr still goes to ~/.sway.log
(errors only without debug, so the timestamps above need `debug = true`).

## Firmware (Legion R9000P ADR10, Insyde RLCN29WW)
Fast Boot / Quick Boot exist but are hidden by the BIOS menu, and already Enabled; Memory Context Restore is Auto (read from efivars, offsets from the RLCN33 image). Click path + pictures: issue #21.
25 boots fall on four values: 5.93 / 6.15 (USB devices plugged in, +0.22) and 7.26 / 7.49 (unexplained +1.33, 7 of 25 boots).
Ruled out for the +1.33s: AC, external monitors, USB, generation change, reboot vs poweroff, time off.
Open suspects: Windows ran in between, keys pressed during POST, battery/EC state; correlate with `firmware=` in boot-timeline.
Cheap lever: PXE Boot to LAN is Enabled → F2 → More Settings → Boot → Disabled (~0.2-1s, inferred). New suspect for the +1.33s: the Realtek PXE driver loading.
BIOS RLCN33WW exists (Windows-only flash); nothing boot-related in RLCN31-33 changelogs.

## Chrome (exec → visible tab loaded, 12.7s)
GPU process 2.2s, loads libEGL_nvidia while rendering on AMD; hiding NVIDIA measured no gain (~320ms launch both ways, warm and cold), so the 2.2s is boot contention.
Lazy restore: own extension (home/config/chrome/lazy_restore) discards inactive tabs on startup; headless A/B: 8/8 restored tabs load → 1/8.
33 extensions, 22 service workers at ~1.26s each; ~20MB content scripts on a github load (ZenHub 9.6MB, Moss 5.2MB).
35 restored tabs compete with the visible one. Chrome lands on ws2 but focus ends on ws1, so the restored tab's first paint waits until you switch to ws2.
